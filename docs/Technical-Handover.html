1. Project Overview

A full web platform for Small Animal Hospital Mumbai (Tata Trusts), comprising a public marketing/informational website, a content-managed admin panel, an OTP-based online appointment booking system, and a reactive WhatsApp chatbot for pet parents.

Public website
Hospital info, specialities, team, facilities, events, blog, media, careers, contact & online appointment booking.
Admin panel
Role-based CMS to manage all website content, appointments, enquiries, notifications & reports.
Appointments
Mobile-OTP login → booking form → status workflow with SMS triggers.
WhatsApp bot
Menu-driven assistant: services, timings, emergency, FAQs, guided appointment booking, "talk to our team".
Live/reference site
sahmumbai.com (existing production reference). This build deploys to a UAT environment.

3. System Architecture

A conventional monolithic Laravel MVC application serving two surfaces from one codebase:

  • Frontend — public routes (routes/web.php), App\Http\Controllers\Frontend\*, Blade views under resources/views/frontend + shared components/frontend.
  • Backend — admin routes behind auth middleware, App\Http\Controllers\Backend\*, views under resources/views/backend + components/backend. Every module is gated by a permission: middleware alias.
  • Webhook — WhatsAppWebhookController at /webhooks/whatsapp (public, CSRF-exempt) for inbound WhatsApp messages.

Key cross-cutting pieces

  • App\Support\WhatsAppBot — the chatbot conversation engine.
  • App\Services\WhatsAppFortius / App\Services\MessageIndiaSms — outbound API clients.
  • App\Support\CommunicationLogger / ActivityLogger — central logging helpers.
  • App\Support\NotificationHooks — raises in-app admin notifications on model events.
  • App\Http\Middleware\CheckPermission — RBAC enforcement (alias permission).

Deploy procedure (UAT)

  1. git pull origin feature/whatsapp-chatbot (code + committed images).
  2. php artisan migrate (schema changes).
  3. php artisan db:seed --class=ModulePermissionsSeeder (permissions & role sync).
  4. php artisan config:clear && php artisan view:clear.
  5. For a queue worker (delayed WhatsApp menu): run php artisan queue:work or a cron/supervisor equivalent.
Important — data vs code. Website content (doctor bios, page text, team members, speciality details) and permission assignments live in the database, not in Git. These do not transfer via git pull — they must be entered in the admin panel or applied via SQL on each environment. Uploaded images live in public/ and are committed to Git.

8. Appointment System

Booking flow (website)

  1. User enters mobile on /user-login → OTP sent via SMS (MessageIndia).
  2. OTP verified → an AppointmentUser (keyed by mobile) is found/created; session established.
  3. Booking form submitted → an AppointmentEnquiry is created with a default status; confirmation SMS + emails fire.

Admin management

  • Appointments — filterable list, per-appointment status change (recorded in an immutable AppointmentStatusHistory), CSV export.
  • Status triggers — statuses can be flagged to fire transactional SMS (e.g. reschedule, cancellation). "Reschedule" statuses require a new future date.
  • Appointment Users — client directory with appointment counts and a Medium indicator/filter (Website vs WhatsApp).
  • Manage Statuses — master list of statuses (name, colour, default/active flags, SMS trigger, requires-date flag).

Website vs WhatsApp appointments

Each appointment carries a source (website / whatsapp) and a per-source reference number (A-0001 for website, WA-0001 for WhatsApp). The same controller/views power two scoped tabs — Appointments (website) and WhatsApp Appointments — with identical functionality. A WhatsApp booking becomes a real appointment when the user completes the pre-filled web form; extra chat-intake fields are folded into the appointment's reason.

9. WhatsApp Chatbot

Provider: Fortius (waba.fortius.in.net) — a transparent proxy over Meta's WhatsApp Cloud API, so payloads follow Meta's format exactly. The chatbot runs inside the 24-hour customer-service window (user messages first), so no approved templates are needed for replies.

Components

  • WhatsAppWebhookController — inbound webhook at /webhooks/whatsapp (GET = verify handshake, POST = messages). Requires a public HTTPS URL (UAT/production only).
  • App\Support\WhatsAppBot — conversation engine: greeting + tappable list menu, services (live from DB), timings/emergency (from Contact Details), FAQs, blog, booking, "talk to our team". Per-user state in whatsapp_conversations.
  • App\Services\WhatsAppFortius — sends text / image / interactive buttons / lists; normalises numbers; logs every send.
  • php artisan whatsapp:simulate — local tester that drives the bot and prints replies (no credentials needed).

Guided booking flow

  1. New / Existing client branch. Existing clients are verified against AppointmentUser by number; an already-registered number is prevented from registering again.
  2. Step-by-step intake (parent & pet details), reason, preferred day/time.
  3. Review step — a summary with a Confirm button; the user can type a field name (e.g. "email") to correct a single answer.
  4. On confirm → a WhatsAppBookingRequest is saved + Customer Care emailed, and the user receives a confirmation + a login link to complete the booking online (the booking becomes a real appointment on web-form submit). Re-using a completed link shows an "already booked — start fresh" notice.
  5. The main menu is re-sent ~30s later via a queued job (SendWhatsAppMainMenu).

"Talk to our team"

Captured messages are saved to whatsapp_team_queries, emailed to Customer Care, and listed under Form Enquiries → WhatsApp Queries.

Delivery constraints: the sending number is a Meta test number — it only delivers to allow-listed recipients, and free-form replies require an open 24-hour session (the user must message first). A verified business number removes these limits. Business-initiated messages (e.g. reminders) require approved Meta templates (planned, not built).

10. Notifications Module

A shared-inbox admin notification system that alerts staff to new activity in real time.

  • Sources — model created events (via NotificationHooks) on Contact Enquiries, Appointments, Job Applications and WhatsApp Queries raise an AdminNotification.
  • Live bell — header bell with unread badge; AJAX polling every ~20s (no WebSockets — a deliberate choice for shared hosting), so new items appear without reloading.
  • Toasts + chime — a clean toast and a soft sound on new activity; a periodic in-app reminder re-surfaces unread items.
  • Notifications page — full list with summary tiles, filters, mark-all-read.

Available to every admin (not permission-gated, like the Dashboard). Reminders are in-panel only (no email reminders).

12. Roles & Permissions (RBAC)

Permissions are defined per module as {slug}.{view|create|edit|delete} in ModulePermissionsSeeder, enforced in three coordinated places: the seeder catalogue, route permission: middleware, and sidebar $can() gates.

RoleAccess
Super AdminAll permissions (also short-circuits to allow everything). Only role with Activity Log, Communication Logs, and delete actions.
AdminView / create / edit on every module (no delete).
Front OfficeAppointments, Appointment Users, Statuses, Contact Enquiries, Reports, Dashboard + WhatsApp Appointments (view/edit) & WhatsApp Queries (view).
Career AdminJob Applications, Job Roles, Join Page.
User (standard)Dashboard only.
When adding a module: add it to ModulePermissionsSeeder ($modules), gate its routes with permission:{slug}.{action}, add a sidebar $can() gate, then re-run the seeder. Custom roles (Front Office, Career Admin) are not auto-synced by the seeder — grant new permissions to them manually.

Permissions table + role assignments are database rows (permissions, roles, permission_role). Run the seeder on each environment; grant custom-role permissions via admin UI or SQL.

14. Scheduled Tasks & Queue

  • Queue — the delayed WhatsApp main-menu uses a queued job (SendWhatsAppMainMenu, 30s delay). With the sync driver it sends immediately; a real delay needs QUEUE_CONNECTION=database (or redis) + a running worker (php artisan queue:work via supervisor/cron).
  • Scheduler — defined in routes/console.php. If scheduled tasks are used, add a server cron: * * * * * php artisan schedule:run.

15. Logging & Auditing

  • Activity Log — audit trail of admin create/update/delete across tracked models, plus login / logout / failed-login events (Super Admin view).
  • Communication Logs — every SMS / email / WhatsApp send attempt with status, error and provider response (Super Admin view).
  • Application logs — standard Laravel logs under storage/logs.

16. Operational / Maintenance Notes

  • Production checklist: APP_ENV=production, APP_DEBUG=false, correct APP_URL (affects OTP/booking links & assets), real MAIL_ADMIN_* inboxes, verified WhatsApp business number.
  • After .env or route changes: php artisan config:clear (and route:clear / view:clear as needed).
  • WhatsApp webhook must be registered in the Fortius panel to the deployed HTTPS URL with the matching verify token, and "Wrapper Client" enabled so inbound is forwarded to the app.
  • Content & permissions are data — manage via the admin panel (or SQL), per environment; they are not carried by Git.
  • Image assets are stored under public/ (e.g. public/our-team, public/home/*) and are committed to Git.

17. Known Constraints & Pending Items

  • WhatsApp test number — deliver only to allow-listed recipients; move to a verified business number for general availability.
  • Outbound WhatsApp templates — appointment status notifications over WhatsApp (confirmed / rescheduled / cancelled) require approved Meta templates — planned, not yet built (SMS equivalents exist).
  • Queue worker — required for the true 30-second delayed menu; otherwise it sends immediately.
  • Content parity — doctor bios / speciality text / images are synced per environment as data; keep in mind when promoting UAT → production.
